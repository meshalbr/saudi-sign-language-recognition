Saudi Sign Language Recognition: Project Log

A system that recognises Saudi / Arabic sign language words from an ordinary camera, laptop or phone, in real time, on a laptop with no graphics card. MediaPipe turns each video frame into body and hand landmark points, and a small Transformer reads the movement of those points over time and names the sign in Arabic and English. This page records what was built, every problem met, how each was fixed, and the measured evidence.

Dataset

KArSL (King Fahd University of Petroleum and Minerals): 502 Arabic sign words, each performed 50 times by 3 professional signers, recorded with a Kinect V2. This project uses KArSL-100, the 100 dynamic signs 0071–0170 (health, verbs, family, places and more). The raw videos are public Google Drive folders on the dataset page; the provided skeleton files were not downloadable, so landmarks were extracted locally.

How it works

camera frame (laptop webcam or phone)
   └─ MediaPipe Holistic ── 33 body points + 21 points per hand (+ face points)
        └─ hand recovery: if a raised hand is lost, run the hand model on a crop around the wrist
             └─ 155 numbers per frame: 9 upper-body points, 2 × 21 hand points (x, y, z),
                2 "hand present" flags; centred on the shoulders, scaled by shoulder width,
                corrected to the 16:9 training aspect
                  └─ sign segmentation: starts when a hand rises, ends when hands are lowered,
                     held still for 1 s, or Done is pressed
                       └─ cleaning: fill short gaps (≤ 8 frames), smooth, trim still frames
                            └─ resample to 32 frames → features: wrist-local hands, velocity,
                               movement trajectory
                                 └─ Transformer encoder (2 layers, 450k weights) → 100 scores
                                      └─ best sub-window search → one Arabic + English answer

The same code path is used for training, evaluation, the OpenCV demo and the web app, so what the model learns is exactly what it sees live.

Training and time

Every model trains for 40 epochs on the laptop CPU with batch size 64, AdamW, a one-cycle learning rate and label smoothing 0.1. The best checkpoint is chosen on validation clips of the training signers (top-1, then lower loss).

Problems and fixes

In the order they were met. Every fix was checked with a measurement or a test.

1. Landmark extraction too slow fixed

Problem
1080p video through MediaPipe on one CPU core would have taken days for 15,000 clips.
Fix
Downscale frames before MediaPipe and run 3 worker processes in parallel.
Evidence
16 test videos: 1.2 min → 0.7 min; full dataset extracted in about 9 hours.

2. Near-perfect on known signers, weak on a new one improved

Problem
99.6% on the official split but 67% on a signer never seen; validation hit 100% while the held-out signer did not.
Cause
The model memorised each signer's hand size and style.
Fix
Hand points relative to the wrist and hand size, heavier regularisation, a Transformer instead of the GRU.
Evidence
67.0% → 83.7% on unseen signers (table above).

3. Checkpoint choice was arbitrary fixed

Problem
Validation accuracy reached 100% early, so every later epoch looked equally good.
Fix
Break ties with validation loss.

4. OpenCV demo window could not be closed or resized; interface unclear fixed

Fix
Resizable window that closes with X, Esc or Q; then a full browser app with Arabic text, which OpenCV cannot draw.

5. Browser version slower than the desktop demo fixed

Cause
Every frame was compressed, sent to the laptop and decoded before MediaPipe ran.
Fix
MediaPipe runs inside the browser on the device GPU; only 155 numbers are sent per frame.

6. Reference videos did not play fixed

Cause
The browser refused to decode the KArSL video files.
Fix
Each reference clip is rendered once into a strip of 24 JPEG frames, cropped to the signer, and animated on the page.

7. Too many flickering guesses fixed

Fix
"Final answer" mode: the stream is cut into single signs and one word is shown per sign; live guesses remain an option.

8. Two-movement signs were split in half (skull) fixed

Cause
The hands vanish for a few frames between the two movements, which ended the sign.
Fix
A sign ends only after 0.7 s without hands, measured in time rather than frames.
Evidence
All 24 skull recordings give one correct answer at 30, 15 and 10 fps.

9. Raising the hand from the lap was read as part of the sign fixed

Cause
KArSL clips start with the hand already raised; the model never saw the raise.
Fix
A sign starts only above a rest line, and the final answer uses the most confident sub-window.
Evidence
Unseen signer with a simulated raise: 60.5% → 68.5%, clean signs unchanged.

10. Phone could not connect; QR code vanished fixed

Causes
Phones need HTTPS for the camera; Windows Firewall blocked the port; results from any camera hid the QR code.
Fix
Self-signed HTTPS, a one-line firewall rule run by the user, relay only from the phone page, one server process for both ports.

11. Hands lost in 22% of training clips improved

Fix
Per-sign quality report; re-extraction of the 15 weakest signs at full resolution; interpolation of gaps up to 8 frames in training and live.
Evidence
Weak signs on unseen signers 82.6% → 85.3%, other signs unchanged.

12. Bug-fix review fixed

Found
Features depended on the camera's shape (upright phone 40% vs 83%); a file-access hole on the reference endpoints; heavy work blocking the server; a crash risk when the laptop page reloaded; the demo mirrored frames unlike training; augmentation leaked values into missing hands.
Fix
Aspect correction to 16:9, id checks, worker threads, safe broadcast, raw-frame landmarking, masked augmentation. 30 tests now cover these.

13. Hands had to leave the frame to finish a sign fixed

Fix
Holding the hands still for 1 s finishes the sign; a bar shows progress. Phone camera gets a lens picker and a wide-angle button.
Evidence
On KArSL, a 1 s hold would end about 2% of signs early (a 0.5 s hold: 10–16%).

14. Trachea read wrong; hand points wrong on the chest improved

Problem
Trachea 64% on unseen signers, mostly read as respiratory device.
Cause
MediaPipe Holistic loses a hand lying flat on the chest (against a striped shirt it lost 32 of 50 frames). Both signs end on the chest, so the model had almost no hand data to separate them.
Fix
When a raised hand is lost, run MediaPipe's dedicated hand model on a crop around the wrist. Same step in the live app. All clips re-extracted overnight.
Evidence so far
Signing-hand coverage on these signs 68% → 97% (worst clip 42% → 96%). After retraining with face points: trachea 64% → 72%, respiratory device 77% → 85%; respiratory device is still read as trachea 14 times out of 150, but trachea is now rarely read as respiratory device (at most 3 times; its main error is pharynx).

16. Laptop running hot during the long extraction fixed

Problem
Three extraction workers kept the CPU boosting at about 130–140% of its base speed for hours.
Fix
Gentle mode: 2 workers, below-normal priority, limited to 4 of the 8 logical CPUs, capped training threads. An earlier version silently failed because the Windows call needed 64-bit handle types; fixed and verified.
Evidence
The workers now use exactly 4 logical CPUs; throughput 18 clips per minute, slightly faster than before because the workers no longer compete.

17. Session ended mid-extraction and left broken files fixed

Problem
209 of 858 saved clips were unreadable after the previous session closed.
Fix
Clips are written to a temporary file and renamed only when complete; broken files were removed and re-extracted.

15. Model relied on where the hand starts and ends tested

Fix
Smoothing, trimming still frames, movement-trajectory features relative to each hand's own position, random hand shifts in training, and dropping badly tracked clips. Compared against recovery-only on all three folds.
Result
84.2% vs 83.9%: no real gain, and trachea fell to 57% because it is told apart from respiratory device only by where it starts. Adding face points as a reference fixed that (85.8%, trachea 72%).
Limit
Trachea and respiratory device differ only in the starting place, so location cannot be ignored completely.
